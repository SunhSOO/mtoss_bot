# MT5·토스증권 시스템 트레이딩 구현 로드맵

## 목적

승인된 시스템 설계를 독립적으로 검토·테스트할 수 있는 여섯 개 하위 프로젝트로 나눈다. 각 단계는 실행 가능한 소프트웨어와 명확한 통과 기준을 제공하며, 다음 단계는 이전 단계의 공개 인터페이스만 사용한다.

## 공통 원칙

- Python 3.12, PostgreSQL 16, Redis Streams, FastAPI, Next.js·TypeScript를 사용한다.
- 모든 금액·가격·수량 계산은 `Decimal` 또는 DB 고정 소수점 타입을 사용한다.
- PostgreSQL이 시스템 오브 레코드이며 Redis는 전달 큐·캐시·lease로만 사용한다.
- 메시지는 최소 한 번 전달하고 멱등 소비자로 실질적인 단일 실행을 보장한다.
- 전략과 신호원은 브로커 API를 직접 호출할 수 없다.
- 브로커 조회 결과가 주문·체결·포지션의 최종 사실이다.
- 각 작업은 실패 테스트 → 최소 구현 → 통과 테스트 → 커밋 순서로 진행한다.
- 실제 브로커 자격증명과 실계좌 주문은 Phase 6 통과 전 사용하지 않는다.

## Phase 1 — 주문 실행 코어

상세 계획: `docs/superpowers/plans/2026-08-18-execution-core-implementation-plan.md`

산출물:

- Python 프로젝트와 로컬 PostgreSQL·Redis 개발 환경
- 공통 신호·목표·주문 계약
- 주문 상태머신과 멱등키
- PostgreSQL 핵심 스키마와 트랜잭션 아웃박스
- 위험 한도와 승인 정책
- 가짜 브로커를 사용하는 신호→주문 수직 슬라이스
- CI에서 단위·통합 테스트 실행

통과 기준:

- 동일 멱등키를 반복 제출해도 브로커 실행 기록이 한 건이다.
- 타임아웃 이후 주문은 `UNKNOWN`이 되며 자동 재실행되지 않는다.
- 위험 한도와 승인 증거 없이 `ExecutionIntent`를 실행할 수 없다.
- DB와 Redis 재시작 후 미전송 아웃박스를 다시 전달한다.

## Phase 2 — 토스증권 어댑터

별도 계획을 작성할 때 Phase 1의 `BrokerAdapter`, `ExecutionIntent`, `BrokerOrderResult` 인터페이스를 그대로 사용하고, 정합성 이슈 계약은 Phase 2에서 추가한다.

산출물:

- OAuth 2.0 토큰 관리와 계좌 헤더 처리
- 시세·종목·거래시간·매수 가능 금액 조회
- 주문 생성·정정·취소·조회
- 공식 호출 한도 헤더를 따르는 limiter
- 409·422·429·500·timeout을 재현하는 토스 모의 브로커
- 미체결 주문·보유 자산 정합성 확인기

통과 기준:

- 같은 `clientOrderId`를 반복해도 주문 한 건으로 수렴한다.
- POST timeout에서 주문 내역 확인 전 재주문하지 않는다.
- `Retry-After`와 `X-RateLimit-*` 헤더가 작업 속도에 반영된다.
- 부분 체결·거절·취소 경합이 내부 상태머신과 일치한다.

## Phase 3 — MT5 노드와 중앙 Python 전략

산출물:

- 사용자별 Windows 서비스와 WSS outbound 연결
- 노드 pairing, 인증서, 단기 토큰, heartbeat
- MT5 계정·심볼·봉·포지션 메타데이터 전달
- 관리자 제공 전략 레지스트리와 제한 실행 환경
- `order_check`·`order_send` 어댑터와 정합성 확인
- 계정별 터미널·데이터 디렉터리 격리

통과 기준:

- 노드가 30초 이상 응답하지 않으면 해당 계좌 주문을 차단한다.
- 재연결되어도 사용자가 승인하기 전 자동매매가 재개되지 않는다.
- 같은 데이터·설정·전략 버전은 같은 신호를 생성한다.
- 만료되거나 서명이 틀린 실행 요청은 노드에서 거절한다.

## Phase 4 — 카피트레이딩 신호원

산출물:

- 리더 계좌 목표 비중 동기화
- HMAC Webhook, nonce, replay 방지
- SEC EDGAR 13F 수집, 수정 신고, CUSIP 매핑 검토
- 계좌별 목표 비중·정수 주 배분
- 신호원별 자동·조건부 자동·수동 승인

통과 기준:

- 리더 주문 수량이 아니라 확인된 포지션 비중으로 팔로워 목표를 계산한다.
- 새 목표 버전이 미제출 이전 계획을 안전하게 대체한다.
- 13F 옵션·매핑 실패·토스 미지원 종목은 주문 대상에서 제외된다.
- Webhook 재전송과 nonce 재사용이 중복 주문을 만들지 않는다.

## Phase 5 — 웹앱과 운영 화면

화면 기준: `docs/superpowers/specs/2026-08-18-claude-design-ui-spec.md`

산출물:

- 초대 전용 로그인, MFA, 관리자·트레이더·조회 전용 RBAC
- 적응형 라이트·다크 AppShell
- 대시보드, 전략, 카피, 승인, 주문·포지션
- 위험 설정, 연결, 감사 기록, 관리자
- 데스크톱·태블릿·모바일 핵심 흐름
- 로딩·빈 상태·오류·offline·긴급 정지 상태

통과 기준:

- 사용자는 자신의 계좌·주문·승인만 볼 수 있다.
- `UNKNOWN` 주문에 재주문 동작이 노출되지 않는다.
- 전체 긴급 정지와 전량 청산이 다른 흐름으로 표시된다.
- 모바일에서 승인과 긴급 정지를 키보드·스크린리더·터치로 완료할 수 있다.

## Phase 6 — 운영 안정화와 제한 실거래

산출물:

- 구조화 로그, metrics, trace, 경보
- KMS·Secrets Manager와 Windows DPAPI 연동
- 백업·복원 자동화와 복구 훈련
- 장애 주입, 메시지 중복·순서 변경, 네트워크 단절 테스트
- 섀도 모드와 계좌별 제한 실거래 gate

통과 기준:

- 재시도·재시작·timeout 시험에서 중복 주문 0건
- 주문·체결·포지션 차이가 자동 해결되거나 수동 조치로 100% 분류된다.
- 10거래일 섀도 운영에서 치명적 오류 0건
- 한 사용자·한 계좌의 10거래일 제한 실거래 gate 통과
- 백업에서 새 환경 복원과 미완료 주문 재구성 성공

## 권장 실행 순서

Phase 1의 각 작업을 구현하고 리뷰한 후 Phase 2 계획을 작성한다. 이 방식은 토스 공식 API와 실제 코어 인터페이스의 차이를 다음 계획에 반영할 수 있고, 아직 존재하지 않는 파일의 줄 번호나 추측성 타입을 장기간 고정하지 않는다. 각 Phase가 끝나면 해당 커밋을 기준으로 다음 Phase 계획에서 정확한 파일과 공개 타입을 다시 잠근다.
